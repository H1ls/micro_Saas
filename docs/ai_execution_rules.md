# AI Execution Rules

Этот файл определяет правила работы AI-разработчика над проектом Micro-SaaS AI Dashboard.

Перед началом **любого нового блока или подзадачи** AI обязан изучить:

1. `docs/mvp_ai_dashboard_architecture_48h.md`
2. `docs/execution_plan.md`
3. `docs/ai_execution_rules.md`
4. `docs/execution_status.md.`
---

# 1. Приоритет документов

Документы имеют следующий приоритет:

```text
docs/mvp_ai_dashboard_architecture_48h.md
                ↓
        docs/execution_plan.md
                ↓
           текущий prompt
                ↓
          существующий код
```

## `mvp_ai_dashboard_architecture_48h.md`

Главный источник истины по:

- архитектуре;
- технологическому стеку;
- границам frontend/backend;
- domain-моделям;
- API-контрактам;
- обработке ошибок;
- AI guardrails;
- ограничениям MVP;
- тому, что намеренно не входит в проект.

AI не должен самостоятельно менять эти решения.

## `execution_plan.md`

Главный источник истины по:

- порядку реализации;
- блокам;
- подзадачам;
- зависимостям между задачами;
- критериям завершения;
- critical path.

AI не должен переходить к следующему блоку, пока текущий блок не завершён.

## Текущий prompt

Prompt определяет:

- какой конкретно блок сейчас выполняется;
- что разрешено изменять;
- дополнительные ограничения текущей задачи.

Prompt не должен использоваться для молчаливого изменения утверждённой архитектуры.

Если prompt противоречит архитектуре или execution plan, AI должен указать противоречие до внесения изменений.

---

# 2. Перед началом каждого блока

Перед написанием кода AI должен:

1. Определить текущий блок в `docs/execution_plan.md`.
2. Прочитать его цель.
3. Прочитать все подзадачи текущего блока.
4. Определить зависимости от предыдущих блоков.
5. Проверить, что обязательные предыдущие блоки уже реализованы.
6. Найти соответствующие архитектурные решения в `docs/mvp_ai_dashboard_architecture_48h.md`.
7. Изучить существующую структуру проекта.
8. Проверить, нет ли уже реализации нужной функциональности.
9. Определить, какие файлы потребуется создать или изменить.
10. Убедиться, что изменения не выходят за scope текущего блока.

Не создавать дублирующие:

- модели;
- schemas;
- services;
- helpers;
- компоненты;
- API routes;
- конфигурационные файлы.

---

# 3. Scope discipline

AI должен реализовывать только текущий блок.

Запрещено самостоятельно переходить к следующему блоку или добавлять функциональность «заодно».

Например, если текущий блок посвящён ingestion, нельзя одновременно реализовывать:

- LLM integration;
- Ask the Data;
- frontend charts;
- vector RAG;
- дополнительные SaaS-функции;
- дополнительные инфраструктурные компоненты.

Даже если это кажется удобным.

Если функциональность относится к следующему блоку — она должна остаться нереализованной до отдельной команды пользователя.

---

# 4. Запрет на overengineering

Это MVP с ограничением разработки в 48 часов.

Без явной необходимости запрещено добавлять:

- PostgreSQL;
- SQLite;
- Redis;
- Celery;
- RabbitMQ;
- Kafka;
- vector database;
- embeddings;
- background workers;
- microservices;
- authentication;
- billing;
- multi-tenant architecture;
- repository pattern;
- сложные generic abstractions;
- дополнительные framework'и;
- инфраструктуру «на будущее».

Не создавать abstraction, если она не нужна текущему MVP.

Главный принцип:

> Сначала законченный работающий продукт, потом улучшения.

---

# 5. Работа с архитектурными противоречиями

Если AI считает, что архитектурное решение:

- невозможно реализовать;
- создаёт техническую проблему;
- противоречит существующему коду;
- приводит к критической ошибке;
- существенно усложняет текущий блок;

он не должен молча менять архитектуру.

Сначала необходимо явно написать:

## Предлагаемое отклонение

**Текущее решение:**

...

**Проблема:**

...

**Предлагаемое изменение:**

...

**Почему это необходимо:**

...

Без такого объяснения архитектурные изменения запрещены.

---

# 6. Работа с существующим кодом

Перед созданием нового файла AI должен проверить:

- нет ли уже подходящего файла;
- нет ли существующей функции;
- нет ли модели с тем же назначением;
- нет ли аналогичного service;
- не создаётся ли второй способ решения одной задачи.

Предпочтительно изменять существующую реализацию, если она соответствует архитектуре.

Не создавать файлы вида:

```text
analysis_service_new.py
analysis_service_v2.py
models2.py
helpers_new.py
temp_service.py
```

вместо нормального изменения существующей структуры.

Не оставлять старую и новую реализацию одной и той же логики без необходимости.

---

# 7. Разделение ответственности

Соблюдать границы, определённые архитектурой.

## API layer

Отвечает за:

- HTTP input;
- валидацию API request;
- вызов service layer;
- HTTP response.

Routes должны оставаться тонкими.

Не размещать в routes:

- CSV/Excel parsing;
- dataframe aggregation;
- LLM prompt logic;
- chart calculations;
- сложную business logic.

## Services

Отвечают за use cases и бизнес-логику.

Основные сервисы проекта:

```text
ingest_service
profiling_service
analysis_service
chart_service
chat_service
session_store
llm_client
```

Не смешивать обязанности нескольких сервисов в одном файле без необходимости.

## Domain

Содержит:

- domain-модели;
- типы;
- controlled domain errors.

Domain не должен зависеть от frontend.

## Prompts

LLM prompts должны храниться отдельно от:

- routes;
- UI;
- domain models.

Prompt logic не должна быть размазана по service и route файлам.

## Frontend

Frontend отвечает за:

- UI;
- interaction;
- rendering;
- локальное состояние интерфейса;
- отображение backend response.

Frontend не должен самостоятельно вычислять бизнесовые агрегаты dataset, если это обязанность backend.

---

# 8. Работа с данными и LLM

LLM нельзя считать доверенным источником данных.

AI может:

- интерпретировать dataset;
- формулировать headline;
- формулировать narrative;
- выделять observations;
- рекомендовать подходящий тип визуализации;
- отвечать на вопросы по dataset.

Но числовые значения и chart data должны по возможности вычисляться обычным backend-кодом.

LLM не должен придумывать:

- колонки;
- значения;
- валюты;
- даты;
- категории;
- метрики;
- события;
- факты, которых нет в dataset.

Если данных для ответа недостаточно, AI должен использовать предусмотренный fallback.

---

# 9. Structured AI output

Ответы LLM, которые используются программно, должны проходить следующий pipeline:

```text
LLM
 ↓
JSON
 ↓
Pydantic validation
 ↓
business validation
 ↓
application
```

Нельзя напрямую доверять raw ответу модели.

Обязательно:

- ограничивать допустимые типы графиков;
- проверять существование `x_key` и `y_key`;
- проверять JSON schema;
- проверять `used_columns` для Ask the Data;
- использовать deterministic fallback при невалидном AI response, если он предусмотрен архитектурой.

---

# 10. Ask the Data guardrails

Ask the Data должен отвечать только по загруженному dataset.

Запрещено использовать внешние знания для ответа на пользовательский вопрос.

Если ответа нет в dataset, вернуть стандартный fallback, предусмотренный архитектурой.

Например:

```text
I cannot answer this from the uploaded dataset.
```

или локализованный эквивалент, если UI работает на другом языке.

Не придумывать ответ ради полезности.

---

# 11. Ошибки

Controlled errors должны проходить через единый error contract.

Не размазывать случайные:

```python
HTTPException(...)
```

по service/domain слоям.

Не отдавать пользователю:

- traceback;
- API keys;
- внутренние stack traces;
- внутренние exception details;
- environment variables;
- чувствительные настройки.

UI должен получать стабильный:

```json
{
  "error": {
    "code": "...",
    "message": "..."
  }
}
```

---

# 12. Проверка после реализации

После каждого блока AI обязан самостоятельно проверить:

- приложение запускается;
- изменённые модули импортируются;
- основные сценарии блока работают;
- существующая функциональность не сломана;
- тесты текущего блока проходят, если они есть;
- ошибки текущего блока возвращаются контролируемо;
- нет очевидных debug-артефактов.

Если execution plan предусматривает тесты — реализовать и выполнить их в рамках блока.

Не считать блок завершённым только потому, что код был написан.

---

# 13. Definition of Done блока

Блок считается завершённым только если:

1. Реализованы все обязательные подзадачи блока.
2. Выполнены критерии `Готово, когда` из `docs/execution_plan.md`.
3. Код запускается.
4. Проверки выполнены.
5. Тесты проходят, если они предусмотрены.
6. Нет известных критических ошибок.
7. Scope блока не расширен.
8. Изменения соответствуют `docs/mvp_ai_dashboard_architecture_48h.md`.
9. Не создана дублирующая логика.
10. Подготовлен краткий отчёт по изменениям.

---

# 14. Отчёт после блока

После завершения каждого блока AI должен показать короткий отчёт.

## Изменённые файлы

Пример:

```text
app/main.py — создан FastAPI application bootstrap
app/api/routes/health.py — добавлен health endpoint
app/domain/models.py — добавлены основные domain-модели
```

## Выполнено

Краткий список завершённых задач.

## Проверки

Указать:

- какие команды запускались;
- какие tests запускались;
- какие API endpoints проверялись;
- результат проверок.

## Не реализовано намеренно

Перечислить функциональность следующих блоков, которую AI сознательно не трогал.

## Архитектурные отклонения

Если отклонений нет, явно написать:

```text
Отклонений от утвержденной архитектуры нет.
```

Если есть — перечислить каждое отдельно и объяснить причину.

# 15. Git workflow

После успешной реализации и проверки законченного блока:

1. Выполнить `git status`.
2. Изучить `git diff`.
3. Проверить, что изменения относятся к текущему блоку.
4. Убедиться, что в commit не попадут секреты и временные файлы.
5. Добавить только относящиеся к текущему блоку файлы.
6. Создать один осмысленный commit.

Использовать Conventional Commits.

Примеры:

```text
feat(backend): add FastAPI foundation
feat(ingest): add dataset normalization
feat(analysis): add structured AI analysis
feat(charts): add dashboard chart pipeline
feat(chat): add ask-the-data flow
feat(frontend): add dashboard upload flow
style(ui): polish dashboard interface
test: cover dashboard core flows
docs: add project setup guide
```

Не добавлять в Git:

- `.env`;
- API keys;
- secrets;
- IDE temporary files;
- debug dumps;
- случайные generated-файлы;
- изменения, не относящиеся к текущему блоку.

После commit показать:

- commit hash;
- commit message;
- список вошедших файлов.

Не выполнять `git push` без отдельной команды пользователя.

---

# 16. Следующий блок

После завершения текущего блока AI не должен автоматически начинать следующий.

Нужно остановиться после:

- реализации;
- проверки;
- отчёта;
- commit.

Следующий блок начинается только после отдельного запроса пользователя.

---

# 17. Critical path

При нехватке времени приоритет имеет основной продуктовый сценарий:

```text
Upload
  ↓
Normalize Dataset
  ↓
Analyze
  ↓
AI Narrative
  ↓
Charts
  ↓
Ask the Data
```

В первую очередь нужно сохранить работоспособность этого flow.

Необязательные визуальные улучшения, дополнительные edge cases и расширения не должны блокировать delivery основной функциональности.

---

# 18. Работа в режиме 48-часового MVP

Перед каждым дополнительным решением AI должен мысленно проверять:

> Нужно ли это для демонстрации основного promise продукта в течение 48 часов?

Если ответ `нет` — функциональность не добавляется без отдельного запроса.

При выборе между:

- более универсальным решением;
- более быстрым и достаточно надёжным решением для MVP;

по умолчанию выбирать второе, если оно не нарушает утверждённую архитектуру.

---

# 19. Главный принцип проекта

AI — исполнитель, технический помощник и reviewer, но не владелец архитектуры продукта.

Рабочий процесс проекта:

```text
Architecture
     ↓
Execution Plan
     ↓
Current Block
     ↓
AI Implementation
     ↓
Validation
     ↓
Review
     ↓
Commit
     ↓
Next Block
```

Главная цель:

> Быстро получить законченный и демонстрируемый Micro-SaaS MVP, сохраняя управляемую архитектуру, контроль над scope и проверяемость AI-generated кода.
